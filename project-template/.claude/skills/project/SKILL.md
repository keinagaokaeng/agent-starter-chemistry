# プロジェクトの進め方

目的: 研究者が「次に何をするか」で考え込んで止まらないようにする。**エージェントが提案し、研究者は選ぶ・決めるだけ**にする。
計画は `PROJECT_PLAN.md`（表の列名は変えない）。数値は同じフォルダの `plan_status.py` で計算する。

## 共通の約束
- 質問は **1 回に 1 つ**、必ず **選択肢 2〜3 個と推奨** を付ける。白紙で「どうしますか？」と聞かない。
- 答えが出ないときは仮の案で進め、`（仮）` と記録して後で見直す。
- ファイルから分かることは聞かずに読み取り、「〜と読み取りました。合っていますか？」と確認する。
- **進捗率・予測日・余裕・SPI は必ず `plan_status.py` の出力から報告する。** 推測で書かない。
  ```
  python3 .claude/skills/project/plan_status.py            # 詳細
  python3 .claude/skills/project/plan_status.py --brief    # 要約
  python3 .claude/skills/project/plan_status.py --write    # plan/STATUS.md と plan/history.jsonl に記録
  python3 .claude/skills/project/plan_status.py <親フォルダ>  # 直下の複数プロジェクトを一覧
  ```
- ゴール・WBS 構造・期限・見込み時間・目標点の変更は承認を得る。状態・実績・ログの更新は報告のみでよい。
  予定どおりに見せるために数値を黙って変えない。

## A. 計画を作る（計画が無いとき、「計画を作って」）

1. **ゴール**: 次を 1 つずつ確定する。
   成果物 / 完了の定義（第三者が判定できるチェックリスト）/ 開始日・期限 / 週あたりの作業時間(h)（少なめに）/ 制約 / 範囲外（やらないこと）
   ゴール文:「〈期限〉までに〈成果物〉を〈完了の定義〉の状態にする。」
2. **WBS**: 成果物（名詞）→ ワークパッケージ（名詞）→ タスク（動詞＋目的語）。番号（1, 1.1, 1.1.1）は ID として後から変えない。
   子をすべて終えると親が完成すること（抜けも重複もない）。
3. **スモールステップ**: 末端タスクは次をすべて満たすまで分割する。
   - 1 回（25〜90 分）で終わる
   - 完了条件が目で確認できる（「ファイル X ができる」「〜を決める」。「検討する」「進める」は不可）
   - 担当（エージェント / 研究者 / 共同）と依存が明確。研究者の作業は最小に（測定・判断・確認）
   - 判断は「判断待ち」表に選択肢と推奨を付けて分ける
   - 各タスクに 見込みh・期日・MS（所属マイルストーン）を入れる。研究者の作業時間も入れる
4. **マイルストーン**: 2〜6 週間に 1 つ。「完了の判定方法」を書く。クリティカルパスの ID に `★`。
5. **品質ルーブリック**: 定性的な目標を 3〜6 観点に分け、0〜3 点の**観察できる基準**を書く（下の D）。
6. **見通しの確認**: 下書きを `$TMPDIR` にコピーして `plan_status.py` で計算する。期限との差がマイナスなら、
   範囲の縮小・期限の変更・作業時間の増加の案を、再計算した数値付きで示す（推奨 1 つ）。
7. 下書きと計算結果を示し、承認後に `PROJECT_PLAN.md` を作る（既存なら上書きせず差分を示す）。`--write` で最初の記録を残す。

## B. 次の一歩（「次は？」、作業の開始時）

1. `PROJECT_PLAN.md` と `--brief` を確認する。「危険」「注意」があれば最初に 1 行で伝える。
   親フォルダで呼ばれたら、一覧を示してどのプロジェクトに取り組むか選んでもらう（推奨付き）。
2. タスクを 1 つ選ぶ: 他を止めている判断待ち → 進行中 → 遅れが見込まれるマイルストーンの ★ タスク → 期日が近いもの。
3. 次の形式で短く提案する:
   ```
   次の一歩: [1.2.2] 1 ファイルで一次反応フィットを行う
   完了条件: results/kinetics/test_fit.csv と残差プロットができる
   最初の 5 分: data/raw/kinetics/40C_run1.csv の列名と単位を確認する
   担当: エージェントが作成・実行 / 研究者は結果を見て判断（2 分）
   見込み: 30 分　→ 進めますか？（はい / 別のタスク / もっと小さく）
   ```
4. 着手したら `状態`=進行中、`開始日`=今日。`AGENTS.md` の安全ルールに従って実行する。予定より大きくなったら区切る。
5. **締めくくり（毎回）**: 完了条件を確認 → `状態`・`完了日`・`実績h`（研究者には選択肢で聞く）・進捗ログ・次の一歩を更新 →
   `--write` を実行し、ゴールまでの距離の変化を 1 行で伝える（例: 「進捗 24% → 29%、M1 予測 01-20 → 01-16」）→ 次の一歩を提案。

**止まっているとき**: 原因を 1 つ推測して対策を 1 つ出す。
大きすぎる → 15〜30 分に分割 / 決められない → 選択肢と推奨、「仮に A で進めて後で戻せる」/
情報不足 → 情報を集めるタスクに置き換え / 気が重い → 5 分の最初の一手だけ / 時間がない → 15 分でできるものを選ぶ

## C. 状況の確認（「状況は？」「間に合う？」）

`plan_status.py` を実行し、この順で短く報告する:
1. 総合判定（順調 / 注意 / 危険）と理由
2. ゴールまでの距離: 作業進捗 %、品質達成率 %、完了の定義 x/y、残り時間
3. 期限の見通し: 完了予測日と期限との差、必要ペース vs 実績ペース
4. 遅れが見込まれるマイルストーン
5. 打ち手 1〜3 個。効果は計画のコピーで再計算した数値で示し、推奨を 1 つ選ぶ

## D. 品質（定性面）を客観的に採点する

- 基準は観察できる事実で書く。客観性の高い順に: 第三者の判定（指導教員・共著者の回答）> 数えられるもの
  （出典のある数値の割合、TODO の数、再生成できる図の数）> 自動指標（スクリプトが `drafts/` の `TODO` と `TODO: verify` を数える）
- 採点はエージェントが**根拠（ファイルと該当箇所、数えた結果）付きで提案**し、研究者が確定する。2 段階の間で迷ったら**低いほう**。
- `評価日` を更新する。14 日以上前の評価は「要再評価」になる。基準や目標を変えるときは理由をログに残し承認を得る。

例: 「数値の追跡可能性 — 0: 出典なし / 1: 半数未満 / 2: 半数以上 / 3: 全数値に出典があり CSV と一致」

## E. 週次レビュー（週 1 回、マイルストーン到達時）

`--write` で記録 → 推移を確認 → 品質を再採点 → 停滞・遅延タスクの対策 → 見積もり倍率（実績/見込み）が 1.3 超なら
未着手タスクの見込み見直し案 → 変更点を示して承認後に `PROJECT_PLAN.md` を更新（タスクは消さず「中止（理由）」）。
マイルストーンは「完了の判定方法」を根拠付きで満たした場合のみ完了にする。
